# Overdue M3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Overdue tell the user what changed without them opening it, through a scheduled server-side refresh that detects and records every change, push notifications for the two moments that matter, and an in-app fallback that works even when push silently fails.

**Architecture:** A GitHub Actions cron hits an authenticated route that processes a bounded slice of tracked items per run, re-queries providers, re-runs the existing resolution layer, diffs against stored state, and appends every difference to `change_log`. Notifications are enqueued rather than sent inline, so a slow provider cannot delay delivery and a failed send can be retried. Push goes out through a Serwist service worker, pulled forward from M4 so it is written once. Because iOS drops push subscriptions silently, the app's own UI is the fallback: Settings surfaces per-subscription health, and the Waiting Shelf marks what changed since the user last looked, regardless of whether a notification ever arrived.

**Tech Stack:** Next.js 16.2.12 App Router, TypeScript, Drizzle ORM, Neon Postgres, Serwist, web-push with VAPID, GitHub Actions, Vitest, Playwright, pnpm 11.17.0.

## Global Constraints

- Package manager is `pnpm`. Never use `npm` or `yarn`.
- TypeScript `strict: true`. No `any` in committed code; use `unknown` and narrow.
- Never use em dashes in any user-facing copy, comment, or commit message.
- There is no authentication in v1. Identity comes from `getCurrentUserId()` in `src/lib/current-user.ts` and nothing else. Do not add Auth.js or sign-in pages.
- There is no email in v1. No Resend, no nodemailer, no email notification path anywhere.
- Release status is computed by `deriveStatus` in `src/resolution/status.ts` and never stored by hand or recomputed inline. It already exists and covers all eight states.
- Release status is always one of: `RELEASED`, `DATED`, `ESTIMATED`, `ANNOUNCED`, `RUMORED`, `EXPECTED`, `HIATUS`, `COMPLETE`.
- `date_precision` is always one of: `day`, `month`, `quarter`, `season`, `year`.
- Provider names are always one of: `manual`, `hardcover`, `wikidata`, `openlibrary`, `google`.
- Manual provider data outranks every other provider on every field, without exception.
- CI never makes live network calls to providers. All provider tests use MSW fixtures.
- Provider adapters never call `fetch` directly and never cast `res.json()` to a shape. They use `fetchJson` and the narrowing helpers from `src/providers/http.ts`.
- `change_log` is append-only. Never update or delete a row in it.
- All dates are handled in UTC. Never use local-timezone methods where a UTC equivalent exists.
- The refresh job is idempotent and sliceable. Running it twice must not double-write, and it must process a bounded slice so a free-tier timeout cannot leave the system in a half-updated state.
- No secret is ever logged, echoed, or written into a response body. That includes VAPID private keys, `CRON_SECRET`, and push subscription auth keys.
- Commit after every task. Never batch multiple tasks into one commit.

## The contract that M2 already depends on

`src/lib/changes.ts` reads `change_log` for Book detail's history. It is built, tested, and currently returns nothing because **no code in this repository has ever written a `change_log` row.** This plan contains its first writer.

That file filters on an exact string:

```ts
const RELEASE_DATE_FIELD = "release_date";
```

**When this plan writes a release-date change, `change_log.field` must be exactly `"release_date"`.** If you write `"date"` or `"releaseDate"`, Book detail's history stays permanently empty and no test fails, because the reader and the writer are tested separately. Task 3 makes this contract explicit and shared so the two cannot drift.

Read `src/lib/changes.ts` before writing Task 3. Note in particular that it excludes rows where `old_value` is null (a first-ever date is not a move) and skips rows whose values do not parse, so a malformed row cannot blank a book's whole history.

## Lessons from M0, M1, and M2 that apply directly

These are not general advice. Each one describes a bug that shipped in this repository and was caught in review.

**Tests that cannot fail are this project's dominant defect.** Four separate instances reached review: a matcher test asserting the wrong paths, a `Map.set` collision making behaviour depend on provider response order, a leap-year boundary sitting on the one date pair that hid it, and colour assertions reading a `data-` attribute while the actual colour came from a different expression. **When you write a test, ask what change would break the code but keep the test green.** If you cannot answer, the test is not yet doing its job. Prove load-bearing tests by mutation: break the code, watch the test fail, revert.

**Mocking a persistence boundary hides real defects.** M1 shipped a bug where every discovered book persisted with a NULL series id, invisible because the per-task tests mocked the persist function. Inject a data source interface and supply fakes. Do not reach for `vi.mock` on your own module.

**A green build is not a passing build.** M2 shipped a page that was silently prerendered as static, which in production would have frozen the Waiting Shelf at build time so newly tracked books never appeared. It was missed because the implementer read a green build as success. **Every task that adds or changes a route must quote the build route table.** Any route reading the database must show `ƒ`, not `○`.

**This repo does not enable React Testing Library auto-cleanup.** Any test file that renders components needs a `@vitest-environment jsdom` docblock and `afterEach(() => cleanup())`. Three files had to be retrofitted in M2.

**The e2e suite runs against a live database containing the developer's own books.** There is no test database. `playwright.config.ts` sets `workers: 1` deliberately, because the specs seed and clear a shared set of fixed ids. Never truncate or mass-delete. Scope every delete to an explicit hardcoded id list, and clear in both `beforeAll` and `afterAll`. `tests/e2e/fixtures/seed-states.ts` is the existing seeder; extend it rather than writing a parallel one.

**Playwright's runner does not load `.env.local`.** `playwright.config.ts` calls `loadEnvConfig` from `@next/env` to fix that. Do not hand-parse env files.

**Never read, print, echo, or grep `.env.local`.** It holds live credentials.

Create `src/db/schema/push.ts`:

```ts
import {
  index,
  integer,
  jsonb,
  pgTable,
  text,
  timestamp,
  unique,
  uuid,
} from "drizzle-orm/pg-core";
import { users } from "./users";

/**
 * One row per browser or installed PWA that granted notification permission.
 *
 * The health columns exist because iOS drops push subscriptions silently when
 * the user deletes and re-adds the home screen icon. Without them a dead
 * subscription is invisible, and since v1 has no email there is no second
 * channel to notice. Settings reads these.
 */
export const pushSubscriptions = pgTable(
  "push_subscriptions",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    endpoint: text("endpoint").notNull(),
    p256dh: text("p256dh").notNull(),
    auth: text("auth").notNull(),
    userAgent: text("user_agent"),
    createdAt: timestamp("created_at", { withTimezone: true })
      .notNull()
      .defaultNow(),
    lastSuccessAt: timestamp("last_success_at", { withTimezone: true }),
    lastFailureAt: timestamp("last_failure_at", { withTimezone: true }),
    failureCount: integer("failure_count").notNull().default(0),
  },
  (t) => [
    // The endpoint is the browser's own identifier for this subscription, so
    // re-subscribing the same device must update rather than duplicate.
    unique("push_subscription_endpoint_unique").on(t.endpoint),
    index("push_subscription_user_idx").on(t.userId),
  ],
);

/**
 * Notifications are enqueued by the refresh job and sent separately.
 *
 * Enqueueing rather than sending inline means a slow provider cannot delay
 * delivery, a failed send can be retried without re-running the refresh, and
 * the daily digest can batch a run's worth of changes into one message
 * instead of several landing at once.
 */
export const notificationQueue = pgTable(
  "notification_queue",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    userId: uuid("user_id")
      .notNull()
      .references(() => users.id, { onDelete: "cascade" }),
    // "digest" or "date_change". Kept as text rather than an enum so adding a
    // kind later needs no migration.
    kind: text("kind").notNull(),
    payload: jsonb("payload").notNull(),
    createdAt: timestamp("created_at", { withTimezone: true })
      .notNull()
      .defaultNow(),
    sentAt: timestamp("sent_at", { withTimezone: true }),
  },
  (t) => [index("notification_queue_unsent_idx").on(t.userId, t.sentAt)],
);
```

Then add to `src/db/schema/users.ts`, inside the existing `users` table definition:

```ts
  lastShelfViewedAt: timestamp("last_shelf_viewed_at", { withTimezone: true }),
```

Nullable deliberately: a user who has never opened the shelf has no baseline, and Task 16 treats null as "nothing is marked" rather than "everything changed", so a first visit is not a wall of badges.

And add to `src/db/schema/catalog.ts`, inside the existing `books` table definition:

```ts
  lastRefreshedAt: timestamp("last_refreshed_at", { withTimezone: true }),
```

This is what Task 4's slice orders by and Task 5's `markRefreshed` writes. A column on `books` rather than a separate `refresh_state` table, because it is one nullable timestamp per book with no other attributes, and a table would be a join for nothing. Nullable means never refreshed, which Task 4 deliberately sorts to the front of the queue.

Re-export both new tables from `src/db/schema/index.ts`, following the pattern already used there.

```ts
import type {
  DatePrecision,
  ProviderName,
  ReleaseStatus,
} from "@/db/schema/enums";

/**
 * The comparable shape of one tracked book at one moment.
 *
 * releaseDate is a string rather than a Date on purpose. change_log stores
 * old_value and new_value as text, and src/lib/changes.ts parses them back
 * with new Date(value). Holding the stored representation here means the diff
 * writes exactly what the reader expects, with no formatting step in between
 * where a timezone could shift the day.
 */
export interface BookSnapshot {
  bookId: string;
  title: string;
  seriesId: string | null;
  seriesPosition: number | null;
  coverUrl: string | null;
  releaseDate: string | null;
  datePrecision: DatePrecision | null;
  status: ReleaseStatus;
  /** Provenance, not a watched value. Recorded on the change, not compared. */
  sourceProvider: ProviderName | null;
}

/**
 * The fields a change is reported for.
 *
 * bookId identifies rather than describes, and sourceProvider is provenance:
 * a field switching from one provider to another with the same value is not a
 * change the user should be told about.
 */
const WATCHED = [
  "title",
  "seriesId",
  "seriesPosition",
  "coverUrl",
  "releaseDate",
  "datePrecision",
  "status",
] as const;

export function snapshotFields(): readonly (keyof BookSnapshot)[] {
  return WATCHED;
}

export function snapshotEquals(a: BookSnapshot, b: BookSnapshot): boolean {
  return WATCHED.every((field) => a[field] === b[field]);
}
```

```ts
import { snapshotFields, type BookSnapshot } from "./snapshot";

/**
 * The exact string src/lib/changes.ts filters on when building Book detail's
 * date history. Reader and writer share this constant so they cannot drift:
 * if they disagreed, the history would stay silently empty and no test would
 * fail, because the two sides are tested separately.
 */
export const RELEASE_DATE_FIELD = "release_date";

/**
 * Snapshot fields are camelCase; change_log.field is snake_case. This is the
 * only place that mapping lives.
 */
export const CHANGE_FIELDS: Record<string, string> = {
  title: "title",
  seriesId: "series_id",
  seriesPosition: "series_position",
  coverUrl: "cover_url",
  releaseDate: RELEASE_DATE_FIELD,
  datePrecision: "date_precision",
  status: "status",
};

export interface ChangeRow {
  entityType: "book";
  entityId: string;
  field: string;
  oldValue: string | null;
  newValue: string | null;
  provider: ProviderName | null;
}

/** change_log stores text, so every value is serialised on the way in. */
function serialise(value: unknown): string | null {
  if (value === null || value === undefined) return null;
  return String(value);
}

export function diffSnapshots(
  before: BookSnapshot,
  after: BookSnapshot,
): ChangeRow[] {
  const rows: ChangeRow[] = [];

  for (const field of snapshotFields()) {
    if (before[field] === after[field]) continue;

    const stored = CHANGE_FIELDS[field];
    if (!stored) continue;

    rows.push({
      entityType: "book",
      entityId: after.bookId,
      field: stored,
      oldValue: serialise(before[field]),
      newValue: serialise(after[field]),
      // The provider that supplied the new value, so the history can show
      // which source moved the date.
      provider: after.sourceProvider,
    });
  }

  return rows;
}
```

```ts
/**
 * How many books one refresh run processes.
 *
 * Bounded because scheduled runs on free tiers are best-effort: a run that
 * tries to refresh everything will eventually hit a platform timeout and leave
 * the system half-updated. A bounded slice always completes, and because the
 * ordering is oldest-first, every tracked item is reached eventually.
 */
export const DEFAULT_SLICE_SIZE = 25;

export interface Sliceable {
  bookId: string;
  lastRefreshedAt: Date | null;
}

/**
 * Oldest-refreshed first, never-refreshed before that.
 *
 * A newly tracked book has nothing to compare against and is the most likely
 * to be wrong, so it goes to the front. Ties break on bookId so two runs over
 * the same data pick the same slice.
 */
export function selectSlice<T extends Sliceable>(
  candidates: T[],
  now: Date,
  size: number = DEFAULT_SLICE_SIZE,
): T[] {
  return [...candidates]
    .sort((a, b) => {
      if (a.lastRefreshedAt === null && b.lastRefreshedAt === null) {
        return a.bookId.localeCompare(b.bookId);
      }
      if (a.lastRefreshedAt === null) return -1;
      if (b.lastRefreshedAt === null) return 1;

      const byAge = a.lastRefreshedAt.getTime() - b.lastRefreshedAt.getTime();
      if (byAge !== 0) return byAge;

      return a.bookId.localeCompare(b.bookId);
    })
    .slice(0, size);
}
```

Note that `now` is currently unused. Keep it in the signature: it is there so a later change can skip items refreshed within some minimum interval without altering every call site. If your linter objects to an unused parameter, prefix it per this repo's ESLint config rather than removing it, and say so in your report.

**A run with no changes writes nothing.** No `change_log` rows, no queue entries. Running the job twice in a row must be a no-op the second time, which is what "idempotent" means here.

```ts
import { getCurrentUserId } from "@/lib/current-user";
import { RELEASE_DATE_FIELD, diffSnapshots, type ChangeRow } from "./diff";
import { selectSlice, type Sliceable } from "./slice";
import type { BookSnapshot } from "./snapshot";

/**
 * Everything the run touches, injected.
 *
 * This is an interface rather than direct imports because M1 shipped a defect
 * (every discovered book persisting with a NULL series id) that its tests
 * missed precisely because they mocked the persistence function. Fakes at this
 * boundary keep the orchestration honestly testable.
 */
export interface RefreshPort {
  candidates(): Promise<Array<Sliceable & { seriesId: string | null }>>;
  currentSnapshot(bookId: string): Promise<BookSnapshot | null>;
  refetchSnapshot(bookId: string): Promise<BookSnapshot | null>;
  writeChanges(rows: ChangeRow[]): Promise<void>;
  markRefreshed(bookIds: string[], at: Date): Promise<void>;
  enqueue(userId: string, kind: string, payload: unknown): Promise<void>;
}

export interface RefreshResult {
  examined: number;
  changed: number;
  changeRows: number;
  failures: Array<{ bookId: string; reason: string }>;
}

export async function runRefresh(
  port: RefreshPort,
  now: Date,
  sliceSize?: number,
): Promise<RefreshResult> {
  const userId = await getCurrentUserId();
  const slice = selectSlice(await port.candidates(), now, sliceSize);

  const rows: ChangeRow[] = [];
  const succeeded: string[] = [];
  const failures: RefreshResult["failures"] = [];
  let changed = 0;

  for (const candidate of slice) {
    try {
      const before = await port.currentSnapshot(candidate.bookId);
      // No stored state means there is nothing to diff against. The book will
      // be picked up once it has been persisted.
      if (!before) continue;

      const after = await port.refetchSnapshot(candidate.bookId);
      // Providers no longer returning the book is not a change worth
      // recording. Deleting our copy on a provider outage would be worse than
      // keeping stale data, since Postgres owns the data.
      if (!after) {
        succeeded.push(candidate.bookId);
        continue;
      }

      const diff = diffSnapshots(before, after);
      if (diff.length > 0) {
        rows.push(...diff);
        changed += 1;

        // The date change is the signature alert and is delivered on its own
        // rather than waiting for the daily digest.
        const dateMove = diff.find((r) => r.field === RELEASE_DATE_FIELD);
        if (dateMove) {
          await port.enqueue(userId, "date_change", {
            bookId: candidate.bookId,
            from: dateMove.oldValue,
            to: dateMove.newValue,
            provider: dateMove.provider,
          });
        }
      }

      succeeded.push(candidate.bookId);
    } catch (error) {
      // One flaky provider must not stop every other book from refreshing.
      // The book is deliberately NOT marked refreshed, so it stays near the
      // front of the queue instead of rotating to the back.
      failures.push({
        bookId: candidate.bookId,
        reason: error instanceof Error ? error.message : String(error),
      });
    }
  }

  if (rows.length > 0) await port.writeChanges(rows);
  if (succeeded.length > 0) await port.markRefreshed(succeeded, now);

  return {
    examined: slice.length,
    changed,
    changeRows: rows.length,
    failures,
  };
}
```

**Note on `markRefreshed`.** It writes `books.last_refreshed_at`, which Task 1 adds. Confirm that column exists before implementing, and if it does not, stop and report rather than silently skipping the call: a `markRefreshed` that quietly does nothing would make every run re-process the same first 25 books forever, and nothing in this task's tests would catch it because they use fakes.

```yaml
# scheduled hour, which cannot support the instant date-change alert. GitHub
# Actions is free and finer-grained, so the schedule lives here.
on:
  schedule:
    # Every six hours. Scheduled runs on free tiers are best-effort and may be
    # delayed or skipped; the job is idempotent and sliceable so a missed run

jobs:

    steps:
      - name: Trigger the refresh slice

          if [ -z "$CRON_SECRET" ] || [ -z "$PRODUCTION_URL" ]; then
            echo "CRON_SECRET or PRODUCTION_URL is not set"
            exit 1

          status=$(curl --silent --show-error --fail-with-body \
            --output response.json --write-out '%{http_code}' \

            --header "Authorization: Bearer $CRON_SECRET")
```

```ts
  id: string;
  userId: string;
  kind: string;
  payload: unknown;
  createdAt: Date;
}

export interface NotificationQueuePort {
  enqueue(userId: string, kind: string, payload: unknown): Promise<void>;
```

`enqueue` here has the same signature as `RefreshPort.enqueue` from Task 5 deliberately, so the Drizzle implementation satisfies both and there is one writer rather than two that can diverge.

`claimUnsent` marks rows sent as it returns them, in one operation rather than two. For a user who already saw the alert, a duplicate is the worse failure.

**Test with a fake transport. No real sends in tests**, which the spec's testing strategy states outright.

The behaviour that carries the milestone's whole risk model:

**A 404 or 410 from the push service means the subscription is dead and must be deleted**, not merely marked failed. **Any other failure records `lastFailureAt` and increments `failureCount`, but keeps the subscription.** A transient push service outage must not delete a working device.

**One failing subscription must not stop the others.** The same isolation rule as the refresh run.

**Every success records `lastSuccessAt` and resets `failureCount` to zero.** Settings reads these, and a device that recovered must stop showing as unhealthy.

The refresh route runs the slice, then drains. Doing both in one request keeps the GitHub Actions workflow to a single call and means a run either completes or fails visibly, rather than leaving notifications stranded behind a second scheduled job that might not fire.

Two rules the tests must pin:

**Date change rows send individually. Digest rows batch into one.** That is the spec's distinction: the date change is the signature alert and earns its own delivery, while the digest respects the batch cadence honestly.

**A claimed row is marked sent before the send is attempted**, not after. If sending throws, the row must not be re-claimed and re-sent on the next run, because a duplicate notification is worse than a missed one for a user who already saw it. The failure is recorded against the subscription instead, which is what Settings surfaces.

# Phase C: The in-app fallback

The spec is blunt about why this phase exists: when iOS drops the push subscription it does so silently, a release date can move with no notification and no signal that anything is wrong, and there is no second channel because email was dropped. These two features make the app's own UI the fallback. The spec calls them mitigations that cost nothing and should be built in M3 rather than treated as optional.

- Produces:

```ts

  rows: Array<{ entityId: string; observedAt: Date }>;
  since: Date | null;
}): Set<string>;

export interface SeenStore {
  lastViewedAt(userId: string): Promise<Date | null>;
  markViewed(userId: string, at: Date): Promise<void>;
```

**The rule for a null baseline needs care.** A user who has never opened the shelf has `lastShelfViewedAt` of null. Treating that as "everything changed" would badge every row on first load, which is noise. Treat null as "nothing is marked", and set the timestamp on that first view so the next visit has a real baseline.

**The ordering problem is the real design question here.** If the page marks the shelf viewed while rendering, a change that arrived seconds earlier is marked seen before the user has looked at it, and it is silently lost. The safe order is: read the baseline, compute badges, render, and only then advance the timestamp. Since a server component cannot reliably run code after the response is sent, **the timestamp advance belongs in a small client-side effect or a route the page calls after paint.** Choose an approach, and **report which and why**, because getting this backwards defeats the feature: a missed change is exactly what this milestone exists to prevent.

**The theme contract constrains the badge.** `ShelfRow` emits exactly four grid slots (cover, identity, status, date) with no markup branching on theme, because M5 ships two more themes as a CSS swap. The badge must live inside one of the four existing slots. Do not add a fifth. `ShelfRow.test.tsx` has a test asserting the four slots in order; it must still pass unchanged.

For `changedBookIds`: a null baseline returns an empty set; rows after the baseline are included; rows before it are excluded; a row exactly at the baseline is excluded (it was visible on the last view); several rows for one book collapse to one id; an empty row list returns an empty set.
